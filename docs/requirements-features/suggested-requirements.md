# Suggested Requirements

## Candidate Additions

- SR-1: Add an automated cross-frontend movement parity test that replays the same enemy seeds and world snapshots for WANDER, PATROL, and AGGRESSIVE modes, and fails if one frontend reintroduces small-area movement loops that the other does not reproduce.
- SR-2: Define `/showenemypath` and `/sep` as a live runtime-path overlay requirement. The overlay shall show the exact active path buffer an enemy is currently following in AGGRESSIVE path-follow and PATROL path modes, and shall not substitute a newly computed shortest path to the player.
- SR-3: Define WANDER collision behavior explicitly. A wander enemy shall keep moving in its current direction until blocked, then choose a random passable cardinal direction, including the immediate reverse direction when that is the random result or the only passable option.
- SR-4: The terminal overlay (opened with T) shall be able to consume the Esc key to close itself. The global Esc handler that pauses/exits the game shall not intercept Esc while the terminal is active.
- SR-5: All enemy-state service instances (PatrolMovementService, AdaptiveAggressiveMovementService, AntiLoopWanderMovementService) shall be fully reset when a new game session starts, ensuring no state leaks from a previous session.
- SR-6: The frontend dispose/cleanup method shall stop and release all running timers (including path-overlay and HUD-message timers) to prevent resource leaks and spurious post-dispose callbacks.
- SR-7: Wall render thickness shall be a single shared constant (`StageConstants.WallThicknessPx`) consumed by all rendering frontends. No frontend may hard-code a wall thickness value; a CI check (or unit assertion) shall verify both frontends read the same value.
- SR-8: Ghost tangibility (phasing) must be fully implemented in both JavaFX and libGDX frontends. A phasing ghost (nonTangibilityEnergy > 0) must pass through walls, be rendered semi-transparent with opacity `clamp(1 − energy/100 + 0.1, 0.1, 1.0)`, and DOES deal contact damage to the player. Only wall-collision checks are skipped during phasing; damage is not suppressed. Automated parity tests shall assert that both frontends behave identically for the same initial energy value. [IMPLEMENTED in GhostNonTangibilityService and GhostPhasingMovementService]
- SR-9: The path-hint P-key feature shall enforce a per-difficulty time budget (Easy: 45 s, Normal: 25 s, Hard: 15 s). Once the budget is exhausted the hint shall become unavailable for the rest of the game and the player shall be shown a clear HUD message. The same budget rules shall apply in both JavaFX and libGDX.
- SR-10: Enemy-player collision detection shall use axis-aligned bounding-box intersection as the primary contact test for all enemy types except phasing ghosts. No additional Euclidean center-distance guard shall be applied on top of the bounding-box test, as this creates false negatives on diagonal approaches.
- SR-11: All shared gameplay constants (board dimensions, character sizes, wall thickness, touch distance, speed defaults) shall reside in `StageConstants` inside the `main.game.maze.mazeworld` module. Constants must never be duplicated or overridden in individual frontend modules.
- SR-12: Enemy damage shall be blocked whenever any maze wall separates the enemy centre from the player centre, regardless of bounding-box overlap. This rule applies to all tangible enemy types in both the JavaFX and libGDX frontends. The wall-crossing test shall use `WallCollisionUtil.wallBetween` / `wallBetweenVectors` and must be covered by unit tests.
- SR-13: Projectile splash damage (e.g. PumpkinBomber) shall also be subject to wall-blocking: if the explosion origin is on the opposite side of a wall from the player, the blast shall not deal damage. This is a separate, deferred concern from melee contact damage.
- SR-14: The per-waypoint dwell time feature (F22: `path.time` in XMI, `N ms` in DSL) is currently not implemented. When implemented, `PatrolMovementService` shall pause the enemy at each waypoint for the configured duration before computing the next leg of the patrol path. Both frontends must honour the dwell time consistently.
- SR-15: Ghost phasing activation trigger should be configurable via the XMI model (e.g., a `nonTangibilityTrigger` attribute). Currently energy is set by game logic directly; externalizing the trigger to the model would allow designers to configure which events cause a ghost to enter phasing mode without code changes.
- SR-16: Add a visual indicator to the HUD when a phasing ghost is active nearby, to give the player a clear signal that a ghost currently bypasses walls and may approach from unexpected directions.
- SR-17: The `GhostPhasingMovementService` direction map grows unbounded over a session when many ghost enemies are present. Add a cleanup hook so entries for dead or despawned enemies are removed to prevent memory growth in long sessions.
- SR-18: The `maze-javafx-backend` module and all future JavaFX-specific modules shall be validated by a dedicated integration test that starts the `App` in headless mode (TestFX or `monocle`), loads a level, and asserts that the game loop starts without exceptions. This guards against silent regressions when dependencies shift between modules.
- SR-19: `ScreenNameFXMLConstants` in `maze-javafx` shall be validated by a unit test that asserts every constant value is a valid resource path resolvable by `getClass().getResource(...)` at runtime. This prevents typo regressions after FXML files are moved between modules.
- SR-20: Module membership boundaries shall be enforced by a ArchUnit or Moduliths test. The rule: no class in `maze-common-backend` may import from `javafx.*` or `main.game.maze.libgdx.*`; no class in `maze-common-frontend` may import from `main.game.maze.libgdx.*`. This prevents future accidental re-contamination.
- SR-21: The `maze` assembly module (launcher) shall contain zero production Java source files other than `Launcher.java`. A CI check should assert `wc -l $(find maze/src/main/java -name '*.java') -gt 1` fails (i.e., fails the build if more than one Java source file is present in `maze/src/main/java`).
- SR-22: Introduce a mandatory shared game session aggregate adoption rule. Both JavaFX and libGDX shall use `GameSession` and `GameMode` from `maze-common-backend` as the only source of truth for mode transitions and session flags (pause, loading, win-save state), and no frontend shall keep parallel duplicate mode state fields once migration is complete.
- SR-23: Add a rendering parity contract test for extracted libGDX views (`GdxGameWorldView`, `GdxHudView`, `GdxOverlayView`) that verifies world overlays and HUD anchor positions remain equivalent to pre-extraction behavior across window resize and difficulty changes.
- SR-24: libGDX frontend bootstrap shall use a `Game` root with `setScreen(...)` routing instead of launching gameplay directly as an `ApplicationAdapter`. During migration, a compatibility adapter may wrap the legacy gameplay class, but all new frontend modes must be introduced as `Screen` implementations.
- SR-25: Texture and media loading in libGDX shall be centralized in a dedicated AssetManager boundary service. Frontend gameplay screens must request assets through this service only; direct `new Texture(...)` creation in screens is forbidden once migration is complete.
- SR-26: libGDX screens shall receive shared dependencies through a single `GameContext` boundary object rather than constructing services directly. New screens must extend a common base screen abstraction to standardize lifecycle behavior, reduce duplication, and improve testability.
- SR-27: Start menu responsibilities in libGDX shall be owned by a dedicated `MenuScreenController`. The menu screen may temporarily route to a compatibility gameplay screen during migration, but difficulty selection and start-loading flow must not remain in the gameplay screen once full extraction is complete.
- SR-28: Active gameplay responsibilities in libGDX shall be owned by a dedicated `PlayScreenController`. During migration, `PlayScreenController` may delegate to legacy behavior through an adapter, but update and draw orchestration must ultimately move out of `GdxGameScreenController`.
- SR-29: Difficulty naming, board dimensions, and board-size labels shall be centralized in dedicated collaborators (`DifficultyBoardConfig` in libGDX plus shared `DifficultyPresentationSupport` in backend modules, or equivalent boundaries) consumed by both `MenuScreenController` and gameplay orchestration. Frontend classes must not duplicate difficulty-switch logic once migration is complete.
- SR-30: Visual style configuration loading in libGDX shall follow one shared policy boundary (`GdxVisualStyleSupport` or equivalent): attempt XMI first, then properties, then `MazeVisualStyleConfig.DEFAULT`. Screens and launcher entry points must not duplicate try-catch loading logic.
- SR-31: Terminal command interpretation in libGDX shall use a shared command support boundary (`GdxTerminalCommandSupport` or equivalent) that maps raw command text to deterministic command outcomes. Gameplay screens may own only the runtime state effects, not duplicated parsing and command mapping rules.
- SR-32: Temporary debug-overlay timer state in libGDX (behaviour label visibility, movement label visibility, enemy path overlay duration) shall be owned by a dedicated runtime state collaborator (`GdxDebugOverlayState` or equivalent). Gameplay screens shall consume this state but shall not duplicate timer bookkeeping logic.
- SR-33: Current-score calculation and high-score persistence in libGDX shall be routed through a shared score support boundary (`GdxScoreSupport` or equivalent). Gameplay screens may coordinate when score changes happen, but score math and repository access shall not be duplicated inline.
- SR-34: Win name entry, trimming, backspace handling, and save preparation in libGDX shall be routed through a shared win score support boundary (`GdxWinScoreSupport` or equivalent). Gameplay screens may own the UI event flow, but name sanitization and save readiness checks shall not be duplicated inline.
- SR-35: libGDX gameplay input shall be handled by a key binding registry that maps logical actions to command objects. Key polling shall be centralized in one input snapshot reader and action dispatch shall run through a router to avoid scattered keyboard checks in gameplay screens.
- SR-36: libGDX gameplay mutable runtime state shall be exposed through a dedicated model boundary so that controller classes coordinate behavior without directly owning every gameplay field.
- SR-37: libGDX frame rendering shall be orchestrated by a dedicated render pipeline that consumes a render snapshot and delegates actual drawing to existing view classes.
- SR-38: libGDX mode specific updates shall be routed through a dedicated mode router that evaluates mode handlers in a deterministic order and returns after the first handling controller.
- SR-39: libGDX gameplay start and reset flow shall be encapsulated in a dedicated bootstrap boundary that initializes arena, runtime model, combat state, and per session runtime flags in one place.
- SR-40: libGDX audio transitions for menu, in game, win, and game over shall be encapsulated behind a dedicated coordinator boundary to keep screen controllers free from direct channel switching policy.
- SR-41: `GdxGameScreenController` construction shall be migrated away from the current telescoping-constructor chain (multiple overloads with four consecutive boolean parameters: `ownsAssetService`, `autoStartOnCreate`, `immediateStartOnCreate`, `showHighScoresOnCreate`). Replace it with a single parameter object / builder (e.g. `GdxGameScreenOptions`) so call sites are self-documenting and adding a new flag does not require touching every overload. This addresses the long-parameter-list / boolean-parameter code smell (CRR-15). Status: implemented. `GdxGameScreenOptions` (immutable options plus fluent builder) now backs a single canonical `GdxGameScreenController(GdxGameScreenOptions)` constructor; all call sites use the builder, and `GdxGameScreenOptionsTest` covers the boundary.

### JavaFX MVC + Command/Registry refactor (Phase 5 of `docs/plans/javafx-gamecontroller-mvc-command-refactor.md`)

These requirements bring the JavaFX frontend to structural parity (CRR-5) with the libGDX MVC + Command/Registry architecture. They are scheduled to be ratified in Phase 5 of the JavaFX refactor plan, on a dedicated branch and pull request separate from the libGDX round.

- SR-42: The Command and key binding registry input core (logical action enum, key binding registry, input frame contract, input router, edge key tracker, and command/context types) shall be shared in `maze-common-frontend` and consumed by both frontends. The dispatch loop shall be generalized over a frontend neutral key type (or a neutral key code with a per frontend adapter) so adding a new key or action does not require modifying the router. libGDX shall be migrated to consume the promoted types so it keeps compiling and its existing input tests stay green.
- SR-43: JavaFX gameplay input shall be handled via the shared key binding registry resolving logical actions to command objects, replacing the inline `handleKeyPressed` switch on `KeyCode`. Key polling shall be centralized in one JavaFX input snapshot reader, and movement, terminal, high scores, spanning tree, path hint, and return to menu shall each be expressed as a command without scattered keyboard checks in the controller.
- SR-44: JavaFX gameplay mutable runtime state shall live in a dedicated model boundary, separate from lifecycle, rendering, input, and FXML concerns, so the controller coordinates behavior without directly owning every gameplay field.
- SR-45: JavaFX gameplay start and reset flow shall be encapsulated in a dedicated bootstrap boundary that initializes arena, runtime model, player configuration, board background, enemies, and per session runtime flags in one place, preserving current setup behavior.
- SR-46: The JavaFX movement thread, movement animation timer, and movement watchdog shall be owned by a dedicated concurrency coordinator with unchanged thread affinity, join timeout, start, stop, and disposal semantics, keeping the controller free of direct thread and timer lifecycle management.
- SR-47: JavaFX mode specific update logic shall be dispatched by a deterministic mode state machine router that evaluates mode handlers in a fixed order and returns after the first handling controller, mirroring the libGDX mode router.
- SR-48: JavaFX frame rendering shall be orchestrated by a dedicated render coordinator that consumes an immutable render snapshot from the gameplay model and delegates actual drawing to existing canvas, HUD, and overlay view helpers, with all scene graph mutation remaining on the JavaFX Application Thread.
- SR-49: JavaFX audio transitions for menu, in game, win, and game over shall be encapsulated behind a dedicated coordinator boundary over `GameAudioDirector`, keeping the controller free from direct channel switching policy.
