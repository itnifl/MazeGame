# Requirements Traceability Matrix

## Scope

This matrix traces game rules (GR), maze generation rules (MGR), features (F) and
approved or implemented suggested requirements (SR) to the design principle, the
implementation and the verification tests, across the JavaFX and libGDX frontends
and the build scripts.

Defects are not tracked here. Open bugs are GitHub issues; a fixed bug's regression
test is listed under the requirement it protects.

## Quality Attributes

1. Maintainability
Code centralizes movement decisions in shared services and exposes a minimal
overlay DTO (`ActivePathPoint`) to keep frontend drawing code thin. Ghost
phasing logic is fully encapsulated in `GhostNonTangibilityService` and
`GhostPhasingMovementService`; both frontends delegate to them.

2. Testability
Movement services are pure enough to execute against `WorldView` stubs and
assert deterministic behavior windows. Ghost phasing services are tested via
unit tests with controlled inputs. New test-double infrastructure
(`CapturingAudioEngine`, `FakeWorldView`, `SpyActionSink`, `CapturingUiScheduler`) isolates
audio-engine, scene-graph, and UI-thread-dispatch dependencies so coordinator
and action tests run without a real game loop.

3. Parity and correctness
JavaFX and libGDX consume the same movement runtime state for enemy path
overlay rendering. Ghost phasing opacity and energy drain are guaranteed
identical via a shared service.

4. Reliability
Configured limits are authoritative: `CompositionResolverImpl.redistributeToTotal(...)`
never exceeds a type's cap (`CompositionResolverImplTest.resolve_capsAreRespected`).
Every fixed defect keeps a regression test in the affected module's test suite.

5. Extensibility (weapons and pickups, SR-239..SR-247)
Item kinds, amounts, damage, reach, sprites, sounds, the spawn interval and the
per-map caps live in the `items` model (`items.ecore` / `items.xmi`), so balancing
needs no code change. Damage and kill credit go through the one `ICanDie` contract
with an attacker id, so a second player only needs a different `PlayerIds` value
(`KillScoringTest.ledgerPerPlayer`). Both frontends call the same `PickupField`,
`PlayerArsenal`, `PowerShield`, `LaserBeamEngine`, `MortalityService.strikeAround`
and `KillScoring` (`GdxWeaponSupportTest`, `FxWeaponsParityTest`).
